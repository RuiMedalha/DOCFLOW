## BUG 1 (HIGH) — payments approve rejects valid cuid IDs

### Symptom
```
POST /payments/payables/<cuid>/approve  →  400 "Validation failed (uuid is expected)"
```

### Root cause
`apps/api/src/modules/payments/payments.controller.ts` applied NestJS's
`ParseUUIDPipe` (UUID v4 regex) to every `:id` path param:

- `GET /payments/payables/:id` (line 78–85)
- `PATCH /payments/payables/:id` (line 113–121)
- `POST /payments/payables/:id/approve` (line 123–137)
- `POST /payments/payables/:id/mark-paid` (line 139–152)
- `PATCH /payments/schedule/:id` (line 195–203)
- `DELETE /payments/schedule/:id` (line 205–216)

But every ID in the schema (`apps/api/prisma/schema.prisma`) is generated by
`@default(cuid())` — e.g. `cmtgjqww70025g52w4e1essfb`. NestJS rejected the
request **before** any service-layer code ran.

### Fix
`payments.controller.ts`:
1. Removed `ParseUUIDPipe` from the import list.
2. Replaced every `new ParseUUIDPipe()` decorator on a `:id` route with a
   plain `@Param('id') id: string` — the service layer already filters by
   `{id, tenantId}` and throws `NotFoundException` on missing rows, so
   invalid IDs surface as 404 instead of 400. The pipes now consume
   `cuid()` strings (length 25, lowercase alnum) without complaining.

### Verification (live throwaway on :4099)

```
$ POST /payments/payables {amount:100, dueDate:2026-09-30}
  → 201 id=cmtgjqww70025g52w4e1essfb

$ POST /payments/payables/cmtgjqww70025g52w4e1essfb/approve {}
  → 200 status="SCHEDULED" approvedById=cmtf1sd640002g5s0nwckw796 approvedAt=2026-08-31T01:31:00.265Z

$ POST /payments/payables/<cuid>/mark-paid {paymentMethod:"sepa", paymentRef:"TEST-PAY-001"}
  → 200 status="PAID" paymentRef="TEST-PAY-001" paidAt=2026-08-31T01:44:41.963Z
```

All three `:id` routes (approve, mark-paid, find/get) accept cuids.

## BUG 3 (HIGH) — `reconciliation/run` infinite recursion / 500

### Symptom
```
POST /reconciliation/run  →  500 RangeError: Maximum call stack size exceeded
```

### Root cause (two compounding defects)

#### 3a. `PrismaService.$transaction` infinite recursion
`apps/api/src/prisma/prisma.service.ts:256-277` (original):

```ts
override $transaction(argOrFn, _options) {
  const ctx = getTenantContext();
  if (!ctx) {
    return PrismaClient.prototype.$transaction.call(this, argOrFn, _options);
  }
  if (typeof argOrFn === 'function') {
    const fn = argOrFn;
    return this.forTenant().$transaction(fn, _options);   // ← recursion
  }
  return this.forTenant().$transaction(argOrFn, _options);
}
```

The pre-auth branch was already routed through `PrismaClient.prototype.$transaction`
because the author knew `forTenant()` would recurse. But the ctx-present
branch went through `this.forTenant()` → `this.inner.$extends(...)` →
wrapped client whose `$transaction` resolves to **this same override**
(since `this.inner === this`, the wrapped object inherits from
`PrismaService.prototype`, where the override lives). Stack trace from
the throwaway on :4099:

```
RangeError: Maximum call stack size exceeded
    at Proxy.forTenant (prisma.service.js:65:14)
    at Proxy.$transaction (prisma.service.js:159:25)
    at Proxy.$transaction (prisma.service.js:159:37)
    at Proxy.$transaction (prisma.service.js:159:37)   × 6000
```

Comment on the original code even warned about this exact bug
("Pre-auth paths (register/login) have no ALS frame. Using forTenant()
here $extends off `inner === this` and recurses through $transaction.")
but only the pre-auth branch had been fixed.

#### 3b. PG17 doesn't have `pg_advisory_xact_lock(bigint, bigint)`
`apps/api/src/modules/reconciliation/reconciliation.service.ts:103-110`
(H-07 design) hashed the tenantId and called
`pg_advisory_xact_lock(${lockKey1}::bigint, ${lockKey2}::bigint)`.
But PostgreSQL 17 only exposes these overloads:

```
pg_advisory_xact_lock(bigint)
pg_advisory_xact_lock(integer, integer)
```

Confirmed by introspection:
```
SELECT proname, pg_get_function_arguments(oid) FROM pg_proc WHERE proname='pg_advisory_xact_lock';
→ (bigint), (integer, integer)
```

So even after 3a was fixed, the first reconciliation call returned
`SQLSTATE 42883 — function pg_advisory_xact_lock(bigint, bigint) does not exist`.

### Fix

#### 3a — collapse the override to a single direct call
`apps/api/src/prisma/prisma.service.ts` — replaced the ctx/no-ctx split
with a single body that always calls `PrismaClient.prototype.$transaction.call(this, ...)`.
The model queries inside the callback stay tenant-scoped because every
service passes `tenantId` explicitly in `where: {...}` (verified by
grepping `apps/api/src/modules/**/services/*.ts` — every call site is
explicit), and the proxy on `this.prisma.<model>` still wraps each
access through `forTenant()`.

#### 3b — switch to the 1-bigint form, namespaced
`apps/api/src/modules/reconciliation/reconciliation.service.ts`:

```ts
// Module-level constant — keeps the lock namespace distinct from any
// other advisory-lock consumer (audit service, future jobs).
const RECONCILIATION_LOCK_NS = BigInt('0x0D0CF10A');

async runMatching(tenantId, userId) {
  return this.prisma.$transaction(async (tx) => {
    await tx.$executeRawUnsafe(
      this.advisoryLockSql(),
      tenantId,
      RECONCILIATION_LOCK_NS.toString(),
    );
    return this.runMatchingInner(tenantId, userId, started, tx);
  });
}

private advisoryLockSql(): string {
  // TenantId and the namespace seed are $1/$2 parameters — never
  // interpolated into the SQL string, so SQL injection is impossible.
  return `SELECT pg_advisory_xact_lock(hashtextextended($1::text, $2::bigint))`;
}
```

`hashtextextended(text, bigint)` returns a bigint in signed-64-bit range,
so `pg_advisory_xact_lock(bigint)` accepts it directly. The namespace
seed (constant `0x0D0CF10A`) prevents collisions with the audit
service's `pg_advisory_xact_lock(hashtext(tenantId))`.

The spec's two stale tests that asserted on the old `advisoryLockKey`
helper were rewritten to assert against `advisoryLockSql` instead.
